# Agent Instructions

- Do not add a commit signature (e.g., a "Co-Authored-By" or "Generated with" trailer) to commits.

## Git & commit conventions

- Use Conventional Commits for commit messages:
  - `feat:` - new feature
  - `fix:` - bug fix
  - `refactor:` - code restructuring that does not change behavior
  - `docs:` - documentation only
  - `style:` - formatting, missing semicolons, etc.
  - `test:` - adding or updating tests
  - `chore:` - maintenance tasks, dependency updates, tooling
  - `perf:` - performance improvements
  - `build:` - build system or external dependencies
  - `ci:` - CI configuration changes
- Keep the commit subject short, imperative mood, and no trailing period.
- Optional scope: `feat(auth): add password reset`.
- Branch naming:
  - `feat/<short-description>` for features
  - `fix/<short-description>` for bug fixes
  - `refactor/<short-description>` for refactoring
  - `chore/<short-description>` for chores
- Avoid mixing unrelated changes in a single commit; split them into logical commits.

## Coding conventions

### Stack

- Next.js 16 (App Router) + React 19 + TypeScript (`strict`) - server components by default; add `"use client"` only where interactivity requires it.
- Tailwind CSS v4 - style with utility classes; the theme tokens live in `app/globals.css`. Keep custom CSS to a minimum.
- MongoDB for persistence via `lib/store.ts`, falling back to `data/db.json` locally when `MONGODB_URI` is unset.
- Capacitor (Android) and Electron (desktop) are thin shells that load the live web app - don't add web features to `android/` or `electron/`; only `electron/main.cjs` and `electron/preload.cjs` are hand-edited.
- Import with the `@/*` alias (maps to the repo root).

### Structure

- `app/` - routes and server components; server actions in per-feature `*-actions.ts` files (e.g. `actions.ts`, `party-actions.ts`, `admin-actions.ts`).
- `components/` - React components grouped by feature (`ui/`, `parties/`, `admin/`, ...); prefer reusing existing `components/ui` primitives over adding new ones.
- `lib/` - shared logic: `store.ts` (DB), `auth.ts`, `types.ts`, `i18n/`, and `ui.ts` (`cn()`).
- User-facing strings go through `lib/i18n` (`tServer` / `t`) for the fa/en switch - no hardcoded UI text.
- **A division page is a workspace, and its parts are declared, not drawn.** `components/division/division-header.tsx` renders the heading every division page shares - the emblem and division name, then the *job* this page does with one plain sentence about it - and the tab row beneath it, so the pages a member moves between look alike. `components/division/document-picker.tsx` is the "what are you writing?" step inside a Paperwork tab, reading a per-division directory (`app/(routes)/divisions/<division>/components/paperwork-documents.ts`): a new format, course report, change to a listing or board is one entry there, and its name is read from the module that writes it rather than retyped. A page opens on the cards and renders a builder only once one is picked - the picker's value starts `null`, and that is what the page reads to decide - never on a document pre-picked for the member. BLS and RED are each a single workspace and show no tab row at all; only FTD keeps tabs, for the jobs that are not paperwork, and a new one of those is one tab. Adding something without offering it is the failure mode - `npm run extension:check` asserts every declared BLS/RED/FTD format, every BLS course report and every board appears in its picker, that the BLS upcoming-courses listing is one card reaching a builder whose dropdown offers each declared change, and that the FTD instructors' board - which is not a paperwork form - is offered on the FTI page.

- **The handbook is files, and the app keeps no other copy of it.** `app/constants/divisions/ftd/handbook.ts` declares the EMR profile section by section - the regular format and the reinstatement one kept apart on purpose - and each section is one BBCode file under `docs/handbook/<format>/`. The FTD Command Handbook tab reads those files and `/api/handbook` writes them back, so an update is either a change in the repository or an honest refusal: the deployed app has no checkout and cannot commit, so it refuses a whole-profile replace rather than pretending the edit stuck. **The tab has exactly one way in and no editor beside it**: one `Update {format.label}` button per declared format, each opening a paste box that shows what the paste would change, and nothing that writes a single section - a section edited on its own is one that no longer agrees with the profile it came from, which is the drift the paste exists to end. `writeHandbookSection` still refuses an edit that drops a section's `mustKeep` placeholders, `writeHandbookSections` refuses to touch a `protectedFromPaste` section, and the route refuses one outright even when a request names it directly, so the profile's own header cannot be replaced by any path - an update is about the phases, and the header is the same on every profile. `npm run handbook:check` asserts the declaration matches the files on disk, that each profile is its own sections in order, and that no handbook source reaches for the store. **The profile an FTO is handed is generated from those files, never kept beside them.** The contract workflow is a client module and cannot read a file, so publishing assembles the sections into `app/constants/divisions/ftd/handbook-content.ts`; that module is generated, `npm run handbook:sync` rebuilds it by hand where the app could not write, and the check fails the moment it disagrees with the files. A second copy of the profile is the drift this replaced - the one in the workflow had already lost TeamSpeak while the files kept it. **Editing the handbook is the Discord admins' and nobody else's**, because it writes the source rather than the store: `isDiscordAdmin` (`DISCORD_ADMIN_IDS`) decides it, the tab is filtered on the server in `divisions/ftd/fd-command/page.tsx` and the endpoint refuses everyone else - and there is deliberately no matrix row for it, since the permission editor must never be able to hand out the ability to write the repository. The tab carries the note that it only works on a local development server, which is the honest reading of a deployed build that has no writable checkout. **A whole profile is pasted in and cut up, not retyped section by section**: a section is found again by its own `[spoiler=…]` heading, so `splitHandbookDocument` (in the same constants module, and pure so the tab can preview the split as it is typed) turns a pasted document back into section files, and the pieces joined with a newline are the paste exactly. Every section has to open and close its own spoilers - one left open buries the next section's body inside this one's collapse, which is why `validateSection` refuses it rather than warning - and `npm run handbook:check` round-trips the split so a section that stopped starting with a heading fails the check rather than sending a paste into the wrong files. The one thing the pieces do not reproduce verbatim is nesting: the live profile keeps its Personnel File Post template inside Certification, so the split hands that enclosing section's closing tag back up to it and every file still stands on its own. **A paste is judged by what it says, not by the app's spelling of it**: a real profile carries the trainer's own name under each signature and spells the member's name the way the forum always has, so a placeholder is matched in any spelling the app fills it by (`app/constants/profile-placeholders.ts` is the one declaration, read by the copy flow that fills it and the check that refuses to lose it), and a protected section's missing placeholders are not the update's business.

- **A pasted profile is converted before anything looks at it, and the conversion is the app's job rather than the member's.** phpBB appends an id of its own to every tag it stores (`[b:1a2b3c4d]` where the forum shows `[b]`), closes a list item with `[/*]` rather than opening the next one, quotes a spoiler's title, and a copy taken off the rendered page instead of out of the editor arrives as HTML with another operating system's newlines - none of it content, and a paste that reached the split as it arrived would fail on the first quoted heading. `lib/handbook-bbcode.ts` is the one converter, and it is pure because the Handbook tab converts as the member types; `lib/handbook-import.ts` is the one whole-profile path, and `npm run handbook:import`, the tab's paste and `POST /api/handbook` all run it, so a paste cannot convert in the app and not in the terminal. Which profile it is comes from the paste's own section headings unless it is said out loud, only the sections that actually differ are written, and only those are judged - a section the paste already agrees with has nothing to warn about. What the converter leaves alone is the writing (spacing, blank lines, spelling), because `npm run handbook:check` asserts that converting a section already in this format changes nothing, which is what makes a paste of an untouched profile write no file. **And the same is true of the order its tags are in, which is the other half of phpBB's spelling.** phpBB closes a tag a writer left open and closes the tags between a closing tag and the one it matches, so the live profile is often not written the way `docs/handbook/**` is - `[b][center]…[/b][/center]` and `…[/center][/b]` are one post to every reader of it. `lib/handbook-markup.ts` is the one place that is decided, and it is pure because the tab decides it as the member types: `canonicalHandbookTags` puts a section's closes in the order phpBB renders them, `compareHandbookSection` counts a paste as already saying what a file says when it is the same text, the same text with its own tags put right, or the same words and tags laid out differently, and `readPastedSections` is the split with that repair applied - per section, because a tag one section left open would otherwise be closed in the next one's file. So a paste of the live profile writes no file at all, and what an update does write is the paste with its tags put right, which is what keeps the forum's spelling from reaching the files. The tab and the whole-profile path ask that one function, since two answers to one question is how a panel promises an update the write then refuses; every section file is already the text the tags are put right to, a section that does differ is reported with the word it parts company at rather than a bare "changed", and all of it is held by `npm run handbook:check` - the fixed point, the repairs, and an end-to-end update that writes nothing while saying what it put right.

- **The FTD Paperwork Guide and Script are built from the handbook rather than kept beside it.** `paperwork/lib/phase-notes/` holds one React component and one spoken transcript per phase, built on `primitives.tsx` - the maroon section headers, chevron bullet lists, OOC pills and click-to-copy command chips a trainer reads. Rendering the raw section in their place was tried and undone: a section is the profile, so a trainer was handed its forms, its placeholders and its paperwork where a guide belongs. So both views are *converted*, not rendered: `paperwork/lib/phase-notes/sections.ts` names the handbook section each phase is drawn from, `src/lib/phase-notes-build.ts` turns that section into the phase's own `.tsx` and its Script (its categories, its steps, its redlined values, its commands, its callouts, with `(( … ))`, backticked commands and `## ` headings kept for Script mode), and `src/lib/phase-notes-write.ts` is the one thing that writes them - `npm run notes:build --write` for every phase, and **an accepted update for the sections it changed**, so a trainer's view is never left saying last month's profile. That is the drift this replaced: the Phase 1 notes still said panic calls do not show in PD/SD dispatch long after the section had stopped saying it. `npm run notes:check` compares both views on the words a trainer reads rather than the markup - a step the section says and a view no longer carries fails, while a sentence a view phrases its own way is reported and passed - and `npm run handbook:check` holds the other side: the profile an FTO is handed, and the fact that every phase names a section that exists and reaches both a Guide and a Script. Two things are deliberately left alone: a section with no steps of its own (the ride-along checklist is the trainers' writing) keeps its views as they are, and a section whose lists do not balance is *read* with the missing `[/list]` put back - a profile is one list of named categories, so a category that starts inside the one before it is a list somebody left open - while `listImbalance` still names the line so the section itself can be fixed.

- **The handbook can be drawn: a tag a section is written in is a tag the renderer knows.** `components/handbook/bbcode-preview.tsx` is the app's one renderer of a section, and only the tags it declares are tracked as tags: a blank written like one (`[Callsign]`, `[Lastname]`, declared in `app/constants/profile-placeholders.ts`) is shown as written and cannot swallow the rest of a section, and a close is applied to the nearest open of its name, so a list nested inside a spoiler is not lost at the close. `npm run handbook:check` fails on any bracket token under `docs/handbook/**` that is neither drawn there nor declared a blank - a format that starts using a new tag is one the renderer cannot read until it is drawn.

### Routes

- **Every page sits under its sidebar section**, and the directory tree mirrors the sidebar exactly: `app/(routes)/divisions/ftd/paperwork`, `app/(routes)/operations/templates`, `app/(routes)/system/changelog`, and so on. A new page goes in the folder of the section it belongs to - don't add a flat top-level route.
- Never type a path in a component. `src/configs/routes.ts` is the `ROUTES` registry; the sidebar, the FTD tab bar, the matrix rows (`ROUTE_META`), the 404 page and the login fallback read from it.
- **A tool whose step changes a user group links into the User Groups page rather than describing it.** `lib/user-groups.ts` builds that link (`userGroupsHref`), naming the group by its `key` so a group this build has not got is a type error, and the page reads the member and the group back out of the query - a promotion, a hire, a reinstatement and an FTD certification all hand over a name the page they came from already holds. A contract workflow declares its link before anybody has typed that name, so it writes the same `{{applicantName}}` token its copy buttons use, and `components/contract/actions.ts` is what puts the filled-in name into a query string. A link may also filter the list to one division's set (`?search=`): `components/division/division-user-groups-link.tsx` names one of the division's own groups and the set's own label comes back (`govGroupSetOf`), so BLS and RED offer their groups from their own header - and FTO Creation from its button row - without any page retyping the forum's name for a division.
- **A tool that opens a page on GOV declares its destinations rather than typing a URL.** The forum's user groups live in `app/constants/gov-groups.ts` - each group's own name, and the UCP page that adds a member to it - and the one page that offers them (`/resources/user-groups`) renders whatever is declared there, in declared sets: the department itself, then its rank groups, then the director posts, then a set per division. A new rank is one entry and a new division is one set, with no page or nav change - and access is `DEFAULT_PAGE_ROLES` (`Employee`), so every member has it and nothing has to be granted. The name is handed over as a marked post, so the extension fills that group page's own `usernames` box on arrival and a browser without it gets the clipboard instead - `npm run extension:check` asserts the box, the group the name was prepared for, and that nothing submits for the member. A copy of the extension older than the one the app ships answers all the same but cannot fill that box, so the tool compares the version it reports (`isVersionOlder` in `app/helpers/forumHandoff.ts`) with the one the shipped folder holds (`readExtensionSummary`) and names the update instead of promising a fill that never arrives - "installed" is not "it can do this". A `g=` URL copied into a component is the drift this prevents.
- **Access is the permission matrix - one stored item, not a table in the repository.** `src/configs/access-matrix.ts` declares the *rows* (`ROUTE_META`), and the rules themselves live in the `access-matrix` item of the Vercel Global Config, edited at `/management/access`. A page with no stored row opens to `DEFAULT_PAGE_ROLES` (`Employee`), a stored row *is* the rule for its route and every page beneath it (longest prefix wins), and `EVERY_PAGE_ROLES` is merged back in on every managed page. A route the redirect layer already answers is deliberately not a row: `/divisions/ftd` is sent to its first tab by a permanent redirect in `next.config.ts`, which runs before the middleware, so a row for the section root would be a decision nothing could reach - `npm run matrix:check` fails on such a row. **Never reintroduce a per-route rule table in `configs/roles.ts`, and never make the repository a second source of a decision** - that duplication is what the matrix replaced.
- **A page is only managed if it is named in `ROUTE_META`**, and `npm run matrix:check` fails when a page in the sidebar or the FTD tab bar has no row, so a new page cannot be added and then forgotten by the editor. A route with no row is not gated at all beyond the employee fallback, which is a wide default, not a safe one.
- **A division's `ranks` list is leadership only, so it is not enough to recognise the division's members.** `membership` names the role everyone in the division holds, so a row meant to admit the whole division has to list both; it is also what `resolveMemberIdentity` reports as `divisionMembership` (the divisions you are in) as opposed to `divisionRanks` (your standing in them), because a generated document's rank line must not print a membership role. FTD deliberately has no `membership`: it is rank-only. A new division needs both fields, or only its leadership can be named.
- `npm run routes:report` prints who each page opens to today, read from the live store (plus the fallback for pages nobody has ruled on), and it typechecks as app code (it imports through the `@/` alias via `scripts/lib/ts-config-loader.mjs`). Run it after changing the matrix or adding a division - it needs no build.
- The entry point `/` has no page. The middleware resolves it per member (`landingRouteFor`) to the first page their roles open, so login and the 404 page send people to `/` instead of one hard-coded destination that only suits some members. Don't add `/` to `redirects()` in `next.config.ts` - a static redirect there intercepts the root before the middleware can run.
- **Never render a nav entry or tab whose `href` the member can't open.** The sidebar is filtered on the server - `app/layout.tsx` runs `filterAccessibleLinks(headerLinks, session.roles, session.discordId)` and passes the allowed hrefs to the client shell - and `app/(routes)/divisions/ftd/layout.tsx` filters the FTD tab bar the same way. Only hrefs travel to the client: nav icons are components and can't cross that boundary, so the client pairs the hrefs with its own icon list rather than deciding access itself.
- When a path moves, add an old-to-new entry to `redirects()` in `next.config.ts` so existing bookmarks and stored `returnTo` values keep working. FTD is one section with a shared tab bar rendered by `app/(routes)/divisions/ftd/layout.tsx`; the per-page layouts beneath it only set metadata.

  - `npm run lint`

### Discord roles

- **One declaration per role.** `src/configs/roles.ts` (`ROLES`) is the only place a Discord role id or display name is written down: `Alias: { id, name }`. It is both the access gate (the matrix names aliases) and the collection the rest of the app reads. Never hand-copy a snowflake or a role name into a constant, a component or a template.
- Everything else derives from it. The ladder (`app/constants/general/ranks.ts`) declares only alias, promotion key and short label, and takes its label and id from the registry; the directors do the same. So adding a rank is one registry entry plus a reference, and renaming one is a single edit that the whole app follows.
- **A division is declared once, in `DIVISIONS` in the same file**: key, `label`, its `ranks` in hierarchy order, its `membership` role, `route` when it has a page, and the `directors` that cover it. Its `route` is the page it owns, not a rule for it - who may open that page is a matrix row like any other - and the `directors` list is what `general/directorRoles.ts` reads back as a director's coverage, so a director's signature and the divisions they cover can't disagree. `ranksForDivision(key)` and `membershipForDivision(key)` are what `app/constants/divisions/*.ts` calls (templates, paperwork and the Staff Page read those rank lists), and `DIVISION_PAGES` in `app/constants/divisions/index.ts` is a full `Record<DivisionKey, DivisionPage>`, so a division declared without a module fails the typecheck. The membership role reaches the division modules through `divisions` (which attaches it alongside `key`) rather than being repeated in each module.
- A rule whose role ids are all blank denies access rather than silently opening, and nothing anywhere guesses a role from its name: an entry with no id is inert. A row naming only id-less ranks therefore closes its page to everyone but HQ, and `npm run routes:report` marks those ranks with `*` while the editor flags every row they appear in.
- The signed-in member's own roles - carried in the session JWT from `guilds.members.read` - are resolved into a rank, division ranks, the divisions they belong to and a director title by `src/lib/member-identity.ts` (pure, no I/O) and served by the `useGuildIdentity` hook. A role whose id is still `null` can never be detected. `heldRoles` is the same resolution the other way round (every role the app can name), and it is what the Staff Page's Discord Profile tab lists - the member's other Discord roles are deliberately not shown.
- `divisionRanks` and `divisionMembership` answer different questions and both are needed: `divisionRanks` is the member's *rank* in a division (what a signature or a generated document prints, and what the Staff Settings tab saves into the per-division dropdowns), while `divisionMembership` is which divisions they are in, rank or not. Filling a signature from `divisionMembership` would print a membership role where a rank belongs; recognising a member by `divisionRanks` alone would hide every division they belong to without a title.
- **Client state and the server-decided shell are two different layers, and a refresh has to move both.** The sidebar, the division tabs and the route gates are decided on the server from the `ftd_auth` cookie; `useGuildIdentity` resolving new roles cannot reach them. So a re-read that moves the roles calls `router.refresh()` (`hooks/useGuildIdentity.ts`) - without it, a section the member just gained or lost stays wrong on the current page until they navigate or sign out and back in, which is what "I had to log in again" means. An RSC refresh is cheap: the middleware sees no document load and the cookie was just re-signed, so it makes no Discord call of its own.
- **Refreshes come in two strengths and the button gets the strong one.** `refreshSessionIfStale` treats `explicit: true` (only `/api/auth/refresh`, only ever from a button) as "a person asked", which skips the age throttle entirely; `force` (a document load, `/api/auth/me?refresh=1`) keeps the short window and everything else waits out the long one. The throttles are there to stop automatic reads from looping into Discord - they must never swallow a click, because a click answered from cache is indistinguishable from a broken feature.
- **A refresh returns an outcome, not a nullable payload.** `RefreshResult` is `{ ok: true, payload, token } | { ok: false, reason }`, and `reason` is one of `no-refresh-token | throttled | not-configured | left-guild | discord-error`. Never collapse these back into a silent `null`: the whole reason "the button does nothing" survived several rounds of fixes is that a failed refresh and a no-op refresh looked identical from the outside. `no-refresh-token` in particular is permanent for that session - the cookie lasts a hundred years, so the member has to sign in again, and the UI has to tell them so.
- **A panel that shows what Discord said must not disappear when Discord says nothing.** `StaffSettingsCard` gates the detected panel on "Discord answered" (a user in the session), never on "something was found": gating it on findings removed the panel, the Sync button and any explanation at exactly the moment a member deleted their last role, which read as the feature breaking. Show the empty state instead, with the button still there.
- **Merging Discord's answer into the Staff Page's saved values is a policy, and it lives in `lib/staff-sync.ts` as pure functions.** `"fill"` (the automatic pass) only writes what Discord reports; `"replace"` (the Sync button) also clears what it no longer reports. Never make the automatic pass authoritative: it cannot tell "the member holds no rank" from "this rank's id isn't in the registry", so clearing there would erase a real member's rank. The mirror rule applies to a division: a saved division rank is only cleared when the member is not in that division at all (`divisionMembership`), never merely because no rank was detected in it.
- **A page load refreshes the session.** The middleware calls `refreshSessionIfStale` (in `lib/session-refresh.ts`, which imports no `next/headers`, so it works in the Edge runtime) on every document request, forces a current read there, and continues with the refreshed payload - so a rank granted in Discord opens its pages on that reload instead of at the next sign-in. Two things are easy to break and worth knowing: the response must also *forward* the re-signed cookie in the request headers (`NextResponse.next({ request: { headers } })`), because server components read the cookie off the request and would otherwise render the old roles on that load; and the throttle (`SESSION_REFRESH_INTERVAL_SECONDS` for background fetches, `FORCED_REFRESH_MIN_INTERVAL_SECONDS` for a load or an explicit read) is what keeps a reload loop from becoming a Discord loop. A failed refresh must always fall back to the cached session - stale roles, never a sign-out.
- **The Staff Page is the source of truth for a member's own details.** Name, signature, rank and director role are saved there (`MedicContext`), and tools read them instead of asking again: `useHighestRank` prefers the saved rank over Discord detection, the FTD paperwork session seeds its signature from it, and the FTD email cards and FTI page read their sender identity straight from `useMedic()` (FTD rank from `divisionRanks`). Add a rank or signature field by reading `useMedic()`, never by asking the member to retype one.
- Never hand-copy a role snowflake into a component, a constant or a template: `src/configs/roles.ts` is the one place an id lives, and it is edited by hand. There is deliberately no sync script - the app is the check. The session refresh re-reads the member's roles on every page load and the registry resolves them, so a stale or wrong id shows up immediately as a member losing the pages their rank should open.
- `id: null` means "the guild has no such role" (or none worth gating on), not "not collected yet". Never invent an id to make a gate appear to work, and never hand-copy one into a component: the registry entry is the id's only home.
- **A role can be granted every page by name instead of by a row, and then the matrix leaves it alone.** `EVERY_PAGE_ROLES` (plus `ADMIN_PAGE_ROLES` for the manager) is that grant, and a registry entry marked `hiddenFromMatrix` is what keeps it out of the editor: the role is not offered in a row's picker, `MATRIX_ROLE_TIERS` never lists it, and `sanitizeMatrix` refuses a stored row naming it, because a row could only ever agree with the code. Legal Faction Management is the one such role - it looks after the faction from outside the department, so it reaches every page including the permission editor, and nobody browsing that editor is told it exists. Hiding a role *without* granting it by name would make it unreachable, which `npm run routes:check` and `npm run matrix:check` both fail on.

### Comments

- Keep comments short and explain *why*, not *what*. Don't write long comments narrating what the code does or what happened - the code should speak for itself. Reserve comments for non-obvious decisions, invariants, and gotchas.
